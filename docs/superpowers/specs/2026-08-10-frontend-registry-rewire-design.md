# Frontend Rewire to InheritanceRegistry — Design Spec

> Phase 1d, expanded scope. Started as two named boxes ("no mock proofs" +
> "poseidon commitment"); discovered mid-exploration that the entire frontend
> contract-integration layer (`blockchain.ts`, `onChainVerifier.ts`,
> `config/contracts.ts`) still targets contracts deleted in Phase 1c's collapse
> (`WillExecutor`, `L1Heartbeat`, the fake `WillVerifier` proof struct). User
> chose the full rewire. Written 2026-08-10.

## What's being replaced and why

- `services/onChainVerifier.ts` — **deleted**. Its own 16-field fake UltraHonk
  proof struct matches nothing real; its actual verification call is
  literally commented out (`return true`). Dead weight, not fixable in place.
- `services/blockchain.ts` — **deleted**, replaced by `services/registryService.ts`.
  1682 lines built around `L1Heartbeat`/`AztecExecutor`/`L1AztecBridge`/`WillExecutor`,
  none of which exist anymore.
- `config/contracts.ts` — **rewritten**. New minimal address set:
  `inheritanceRegistry`, `usdc`, `selfVerifier` (the only three contracts the
  frontend calls directly — `WillVerifier`/`HonkVerifier`/Poseidon are internal
  to the registry, never called from the frontend).
- Hand-written `viem` ABIs (human-readable `parseAbi` strings, matching the
  existing code style) for the three contracts + standard `IERC20`, committed
  in the frontend. No build-artifact sync pipeline — the frozen interface
  discipline from Phase 1a/1b (documented signatures, not auto-synced files)
  is the same trust model already used for the circuit's public inputs.

## Key realization: register needs no proof

`InheritanceRegistry.register(bytes32 commitment, uint256 merkleRoot, uint256 totalEth, uint256 totalUsdc, uint256 totalNftCount) payable`
takes **no proof parameter** — only the commitment, root, and totals. The proof
is only required at `executeWill`. This means:
- Register no longer needs to load `noir_js`/`bb.js` (the heavy wasm proving
  stack) at all — just the lightweight Poseidon helpers in `lib/poseidon.ts`
  (already what `generateWillCommitmentAsync`/`generateMerkleRootAsync` use).
- The full witness (salt + beneficiary arrays) is only needed again at
  **execute** time, by whoever executes — see below.

## Decisions locked with the user

1. **Claims: manual claim-entry form.** No "browse wills you might be in" list.
   Beneficiary data (leafIndex, ethAmount, usdcAmount, siblings) is
   intentionally off-chain (that's the privacy point) — the will owner shares
   it with each beneficiary out-of-band. The old code faked this entirely
   (`"For demo purposes: Allow claiming from any executed will"`, no real
   eligibility check) — the honest version has no discovery, just entry.
2. **`/withdraw` → honest explainer.** Route and nav link kept; content
   replaced explaining there is deliberately no owner-recall function once a
   will is sealed (a trust property, not a gap), linking to `/execute` and
   `/claims`.
3. **One spec, staged commits.** This document covers the whole rewire;
   implementation lands as several sequenced commits sharing the new service API.

## New service layer: `registryService.ts`

Keeps the still-valid generic wallet infra from `blockchain.ts`
(`connectWallet`, `getChain`, client setup, `getBalance`, `waitForTransaction`,
`getTransactionStatus`) and replaces every contract-specific method:

```
isSelfVerified(address): Promise<boolean>                  // SelfHumanVerifier.isFullyVerified — read
register(commitment, merkleRoot, totalEth, totalUsdc): Promise<Hash>
  // approves USDC (if totalUsdc > 0) then registry.register(..., totalNftCount=0), value=totalEth
getMyWill(owner): Promise<WillRecord | null>                // WillRegistered event log filtered by owner; most recent
getWill(commitment): Promise<WillRecord>                    // registry.getWill — view
checkIn(commitment): Promise<Hash>
triggerGracePeriod(commitment): Promise<Hash>
veto(commitment): Promise<Hash>
isVetoMember(address): Promise<boolean>                     // registry.isVetoMember — view
getVetoMembers(): Promise<Address[]>
executeWill(commitment, proof): Promise<Hash>                // proof: bytes, generated by noirService just before this call
claim(commitment, ethAmount, usdcAmount, leafIndex, siblings): Promise<Hash>
```

`WillRecord` mirrors the contract's `Will` struct (owner, merkleRoot, totalEth,
totalUsdc, registeredAt, lastCheckIn, graceStart, graceEpoch, vetoCount,
executed, exists).

## noirService cleanup (original box 1)

- `initialize()`: no more swallow-into-fake-success. If the circuit artifact,
  `noir_js`, or the UltraHonk backend fail to load, **throw**. The existing
  `WalletContext` `initializeServices` effect already catches and surfaces
  `error` — confirmed nothing gates on that state today (no disabled buttons),
  so this is a safe, purely-informational change in blast radius.
- `generateWillProof()`: delete the "Fallback: mock proof" branch entirely
  (returning `proof: '0x'`). If backend/execute/proving fails, throw with the
  real error. `generateWillCommitmentAsync`/`generateMerkleRootAsync` are
  unaffected — they're pure Poseidon, no backend dependency, used at register
  time without triggering heavy initialization.
- Delete the dead, always-true `verifyProof(proof, publicInputs)` method
  (zero external callers — confirmed by grep).
- Delete `initializeOnChainVerifier`/`registerWillOnChain`/`verifyProofOnChain`/
  `executeWillOnChain`/`testOnChainVerification` — these were thin pass-throughs
  to the now-deleted `OnChainVerifierService`. Proving and chain calls become
  cleanly separated: `noirService` only proves, `registryService` only calls chain.

## Page-by-page changes

### `register/page.tsx`
- Compute the **real Poseidon commitment** via `generateWillCommitmentAsync`
  and display it on the sealed-success screen (design.md §7 already specified
  "sealed success with the commitment shown once" — currently shows the salt
  instead; this was always the intended target, just unreachable before).
- Delete the dead `willCommitment = "0x"+salt+Date.now()` line (confirmed inert
  — nothing downstream reads it; the real commitment always came from
  `noirService.generateWillProof`, now from the direct Poseidon call).
- **Remove the NFT input fields** (step 1 "Total NFTs", per-beneficiary "NFTs").
  The registry rejects `totalNftCount != 0` — leaving inputs that always cause
  a revert is a real correctness bug, not a style choice. Every beneficiary's
  nft field is hardcoded to `"0"`, consistent with the circuit leaf hash.
- Call `registryService.register(commitment, merkleRoot, totalEth, totalUsdc)`
  directly — no proof, no `noirService.generateWillProof` at register time.
- Pre-flight check `isSelfVerified(account)` before allowing submit; surface a
  clear message if not verified (the actual Self QR-verification completion
  flow itself is untouched — that's Phase 1d box 4, separate work).

### `checkin/page.tsx`, `veto/page.tsx`
- Both currently call zero-arg `checkIn()`/`castVeto()`/`getVetoStatus()`
  against the deleted single-owner `L1Heartbeat`. Fix: resolve "my will" via
  `getMyWill(account)` (event-log lookup by owner) once per page load, then
  call the per-will functions (`checkIn(commitment)`, `veto(commitment)`,
  `triggerGracePeriod(commitment)`) against it. No will found → the existing
  "no will sealed yet" empty state (already handled in checkin's UI).
- Veto membership check via `isVetoMember(account)` (real read, replacing the
  old `getVetoStatus()` blob).

### `execute/page.tsx`
- Execution needs the full witness (salt + beneficiary arrays) to regenerate
  the exact proof — which the chain never stored (that's the privacy point).
  This data must come from whoever is executing (typically the owner, who was
  already told "keep your will salt safe" at seal time — this is the existing,
  already-anticipated contract with the user, not a new burden).
- Replace the list of `getAllRegisteredWills()` with a compact re-entry form:
  paste `willCommitment` + salt + beneficiary data → generate the real proof
  client-side via `noirService.generateWillProof` → call
  `registryService.executeWill(commitment, proof)`.
- Delete `executeWillSimple`/`executeWillAlternative` (the two-method
  try-fallback hack) — one real call, real errors.

### `claims/page.tsx`
- Manual claim-entry form (decision #1): `willCommitment`, `ethAmount`,
  `usdcAmount`, `leafIndex`, 3 sibling hashes → `registryService.claim(...)`.
  Drop the executed-wills scanning list and the fake `checkAndExecuteWills`
  auto-execute-for-anyone behavior.

### `withdraw/page.tsx`
- Replace with the honest explainer (decision #2). Delete the
  `knownWillCommitments` hardcoded guess-list and `directWithdrawEth` entirely.

### `app/page.tsx` (dashboard)
- Wire the placeholder stat tiles ("Wills sealed", etc. — already commented
  `// placeholder counts until data wiring in Phase 1d`) to `getMyWill`.
  Small, additive; not required for correctness, included since it's cheap
  once `getMyWill` exists and closes a comment that names this exact phase.

## What this closes vs. leaves open (Phase 1d box list)

- ✅ box 1 "no mock proofs" — done via noirService cleanup above.
- ✅ box 2 "poseidon commitment" — done via register's real commitment display
  (the withdraw half of this box is superseded by withdraw's removal).
- ✅ box 3 "real on-chain verify in onChainVerifier" — subsumed: the file is
  deleted, replaced by real calls through `registryService`.
- ⬜ box 4 "real Self verification" — **not** done here. `register` gains a
  real on-chain `isFullyVerified` pre-flight read, but the underlying
  `SelfProtocolService.waitForVerification` QR-flow completion is still faked
  via `setTimeout` — that's separate, untouched work.
- ⬜ box 5 "e2e test" — separate follow-up once this lands.

## Config / env

`config/contracts.ts` keeps the existing multi-network table shape
(localhost/sepolia/celo-sepolia/mainnet) but each network's `contracts` shrinks
to `{ inheritanceRegistry, usdc, selfVerifier }`. All default to the zero
address (nothing is deployed yet — Phase 1e) with `NEXT_PUBLIC_*` env overrides,
matching the existing RPC-URL override pattern. No addresses are invented here.

## Out of scope (explicitly)
- Deploying anything (Phase 1e).
- A real off-chain channel for owners to share claim data with beneficiaries
  (e.g. encrypted export/QR) — claims gets a manual-entry form, not a
  distribution mechanism. Worth a future phase if desired.
- The Self QR-verification completion flow (box 4).
- Multi-will-per-owner UX (checkin/veto/dashboard assume one will per
  connected address, via "most recent registration" — matches existing UI
  assumptions, which already model one will per user).
